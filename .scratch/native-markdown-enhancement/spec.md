# GitHub 原生 Markdown 编辑器增强扩展：首版开发 Spec

Status: ready-for-agent
Label: ready-for-agent
Version: v1
Date: 2026-09-24

## Problem Statement

在 GitHub 上写 Issue 或编辑 README 时，用户需要手写并记住提示块、折叠块等 Markdown 语法。一个 Issue Form 可能同时有多个正文输入框，手动复制片段容易放错位置。用户希望从正在使用的编辑器按钮区域直接选择格式，内容立即进入对应的 GitHub 原生编辑器，同时继续使用已有的编辑、预览、撤销、上传和提交流程。

已有设计与官方来源表明，Issue 正文和 README 文件编辑采用不同的编辑环境。能够追加按钮，不等于能够可靠地写入正文、同步 GitHub 页面状态并保留原生撤销。首版只有同时覆盖两类编辑器，才满足本需求。

## Solution

交付适用于 Chrome 和 Edge 的 GitHub.com 桌面浏览器扩展。在每个可确认的 Issue Markdown 正文编辑器，以及 README/其他 Markdown 文件的原生文件编辑器旁，放置一个对应的“增强 ▾”入口。用户从菜单选择插入命令，扩展按照该**编辑器实例**的**选区快照**生成 Markdown，并通过已验证的原生编辑路径写入。Write / Preview、文件预览、草稿、撤销/重做和保存/提交继续由 GitHub 负责。

首版菜单提供 NOTE、TIP、IMPORTANT、WARNING、CAUTION 五种**提示块**，以及 Details 折叠块、Keyboard 按键标签和 Diff 代码块，共八个**插入命令**。一个 Issue Form 中每个合格的 Markdown 正文框都有自己的入口；代码渲染字段等非目标输入框不增加入口。README 在自己的文件编辑操作区域显示同一菜单，不仿造一整套 Issue 工具栏。

交付物包括可本地加载的 Chrome/Edge 扩展、基于真实功能编写的安装及使用说明、针对性测试，以及记录浏览器版本和页面变体的验收结果。交付判定要求 Issue 和 README 两类场景均通过实页验证；仅完成其中一种不能标记首版完成。

## User Stories

1. 作为新建 Issue 的用户，我希望在正文工具栏看到增强入口，以便直接选择 Markdown 格式。
2. 作为编辑已有 Issue 描述的用户，我希望入口随原生编辑器出现，以便继续修改原有正文。
3. 作为撰写 Issue 评论的用户，我希望在评论编辑器使用增强入口，以便插入提示信息。
4. 作为编辑已有普通 Issue 评论的用户，我希望入口跟随编辑状态出现和消失，以便页面不留下无效按钮。
5. 作为填写多字段 Issue Form 的用户，我希望每个 Markdown 正文框各有一个入口，以便在需要的字段使用增强功能。
6. 作为填写多字段 Issue Form 的用户，我希望在第二个框执行命令时只改变第二个框，以免覆盖其他字段。
7. 作为填写含日志/代码字段的 Issue Form 的用户，我希望这些字段保持原来的代码输入方式，以免格式化命令破坏代码内容。
8. 作为编辑 README 的用户，我希望在 GitHub 文件编辑器旁看到增强入口，以便直接插入 Markdown 片段。
9. 作为新建或编辑其他 Markdown 文件的用户，我希望获得与 README 相同的增强功能，以便复用同一工作方式。
10. 作为修改文件名的用户，我希望入口随文件是否为 Markdown 重新判断，以免在非 Markdown 文件中出现无关操作。
11. 作为写作者，我希望能选择五种提示块，并看到各自的简短用途，以便不再记忆类型名。
12. 作为写作者，我希望无选区时插入可立即替换的提示块正文，以便继续输入。
13. 作为写作者，我希望选中多行后能将这些行放入所选提示块，以便保留原文内容和顺序。
14. 作为写作者，我希望将文字包入 Details，或插入含标题与正文占位的 Details，以便收纳较长背景信息。
15. 作为写作者，我希望插入或包裹单行 Keyboard 标签，以便标记按键文字。
16. 作为写作者，我希望插入 Diff 围栏并保留选中的代码原文，以便展示差异格式。
17. 作为写作者，我希望命令只改变光标或选区附近的内容，以便保留整篇文档的其他文字。
18. 作为写作者，我希望点击菜单后仍使用打开菜单前的光标与选区，以便内容落在预期位置。
19. 作为同时编辑多个框的用户，我希望菜单始终绑定打开它的框，以免焦点切换造成串框写入。
20. 作为键盘用户，我希望能打开菜单、移动到命令、执行和取消，以便不依赖鼠标。
21. 作为使用辅助技术的用户，我希望按钮与菜单状态有清楚的名称和焦点反馈，以便判断可用命令。
22. 作为使用深色、高对比或窄窗口界面的用户，我希望菜单文字清晰、完整可见，以便完成选择。
23. 作为使用中文输入法的用户，我希望组合输入不中断，以免产生残缺文字。
24. 作为使用 GitHub Preview 的用户，我希望预览立即反映插入结果，以便确认 Markdown 渲染效果。
25. 作为使用撤销/重做的用户，我希望一次增强操作可作为一次原生编辑撤销并重做，以便继续使用已有编辑历史。
26. 作为使用 GitHub 原有格式按钮、提及、上传和提交快捷键的用户，我希望这些能力继续正常工作，以便保留熟悉的写作流程。
27. 作为在页面内导航、切换预览或关闭编辑框的用户，我希望旧菜单和旧选区失效，以免命令写进错误的页面或文件。
28. 作为遇到暂不支持的编辑器的用户，我希望看到简短原因或保持原生页面可用，以免扩展猜测目标并损坏草稿。
29. 作为隐私敏感仓库的用户，我希望正文和选区不被持久化或上传，以便扩展只在本地完成插入。
30. 作为安装扩展的用户，我希望安装说明如实列出已验收的浏览器和页面，以便知道何处可用。

## Implementation Decisions

- 首版目标是 `github.com` 桌面网页上的 Chrome/Edge 扩展。README 是必需场景；普通 Issue、新建/编辑 Issue 描述、普通 Issue 评论及包含多个 Markdown 正文框的 Issue Form 是必需场景。其他 Markdown 文件创建/编辑使用同一文件编辑器适配。PR、Discussion、Wiki、github.dev、GitHub Enterprise、移动端和 Review 专用评论不在本版范围。
- **原生编辑器**指 GitHub 提供的正文或文件编辑区域。扩展只能追加自己拥有的增强入口与浮层，并向当前编辑器提交局部编辑。保留原有编辑器节点、按钮顺序、Write / Preview、文件预览与提交入口；不替换、不克隆、不重挂载原生编辑器，也不维护第二份常驻正文。
- 每个增强入口只归属一个**编辑器实例**。识别器须确认输入区、按钮区、编辑模式和唯一关联；无法消歧则不挂载。优先利用经实页确认的工具栏和输入区明确关联，不能用“页面第一个 textarea”或翻译后的标题文字推断目标。
- Issue Forms 中 `render` 代码字段、标题、搜索框、只读/禁用输入区及非 Markdown 文件不得挂载增强入口。即使代码字段的语言名为 `markdown`，只要它是代码渲染字段，仍然排除。
- 入口为 `type="button"`，不可触发表单提交。首版菜单单层分组，五种提示块直接显示，另列 Details、Keyboard、Diff；只允许一个菜单展开。中文界面使用“增强”，英文界面使用“Enhance”。菜单提供类型文字和用途，不单靠颜色传达含义。
- 菜单支持鼠标和键盘操作。Enter/Space 打开，方向键和 Home/End 移动，Enter 执行，Escape 关闭并返回入口，Tab 关闭并保持自然焦点顺序。菜单自身处理按键，不占用 GitHub 的全局编辑快捷键；实现可访问的名称、状态和焦点管理。
- 打开菜单时捕获目标实例、文件/页面身份、内容版本和**选区快照**。执行前重新确认目标仍存在、仍可写、仍是同一文档、内容与选区未失效、没有正在进行的输入法组合。过期操作取消，不自动套用旧偏移；切换焦点到另一编辑器不改变菜单目标。
- 命令生成与编辑器写入分开。命令根据快照生成局部编辑计划与完成后的选区，不访问 GitHub 页面。Issue 文本框和文件编辑器分别实现读取、能力判断、提交和清理；除确有实测需要外，不增加桥接层或大型编辑器依赖。
- 提示块无选区时插入类型头和可选中的正文占位；有选区时每行成为引用正文，保留原文和空行。Details 将选区放入折叠正文，无选区时插入 summary/正文占位。Keyboard 仅处理单行选区，并转义 HTML 特殊字符；多行选区显示不可用原因。Diff 用足够长的围栏安全包住原文，不猜测新增/删除行。
- 块级命令只补足所需段落空行，不格式化全文，不删除范围外内容。对于可识别的代码围栏内部、嵌套列表或引用环境，若无法保证产出预期顶层块，则禁用并给出原因。所有命令保持选区之外的文本逐字不变。
- Issue 适配的写入方式必须在真实 Chrome/Edge 页面证明：GitHub 页面状态接受修改、Preview 保留内容、后续输入不会回退，插入进入原生撤销/重做历史。单纯改 textarea 值并派发事件，不能被视为合格写入。任何候选方法只有通过这些行为检查才可用于交付。
- README 使用独立文件编辑器适配。先在真实页面确认编辑器实例、可用的事务路径和原生历史，再冻结具体访问方式；不能从渲染 DOM 读取整篇文件、直接修改可编辑 DOM，或假定扩展自带的 CodeMirror 包能访问 GitHub 内部实例。若没有满足本 Spec 的可靠写入方式，应报告阻塞，不能把复制片段或“仅支持 Issue”作为首版完成。
- 只有 README 的真实接入需要跨页面运行环境时，才考虑最小的 MAIN world 桥接。桥接只允许绑定实例的探测、快照和结构化编辑；校验目标、版本、范围、大小和重复请求，不提供任意代码执行、方法调用、网络或扩展权限代理。超时后不得盲目重试写入。
- 动态编辑器通过实例注册和局部 DOM 变化识别挂载、移除和重建。重复扫描不产生重复入口。Preview、取消编辑、路由/文件变化和实例移除须关闭菜单、失效快照并释放监听器；单实例失败不影响其他编辑器。
- 扩展只申请覆盖目标 GitHub 网页及经验证接入方式所需的最小权限。不需要 GitHub Token、后台服务、远程模板、剪贴板读取或正文上报；正文、选区和快照仅在执行命令期间保留内存，不写日志或持久化。
- 先完成 Issue 与 README 的最小 Note 插入探针，再扩展全部八个命令。真实页面的实例访问、状态同步、撤销/重做属于实施前置门槛；门槛失败时停止对应实现并记录证据，不能放宽原生编辑器保留要求。

## Testing Decisions

- **主要测试接缝**是用户可见的“增强入口 → 选择命令 → 对应 GitHub 原生编辑器文本、选区、预览和撤销状态”完整行为。优先在真实 GitHub 页面验证这个接缝；组件内部的选择器名称、DOM 层级和函数调用顺序不是通过标准。
- 当前仓库没有代码和既有测试先例。先使用少量本地夹具验证受控 textarea、三个正文框加一个代码字段、动态编辑器重建，以及文件编辑器适配契约；夹具结果不能替代真实 GitHub 验收。
- 命令转换逻辑单独测试输入/输出与选区边界：空文档、行首/行中/行尾、正反选区、多行及空行、Unicode/emoji、换行、HTML 转义和含反引号的 Diff 内容。只断言生成文本、保留的范围外文字与下一选区，不测试内部实现步骤。
- Chrome 和 Edge 都要在真实 GitHub 页面对普通 Issue、至少三个 Markdown 框并混入代码字段的 Issue Form、新建/编辑描述与评论、README 编辑、Markdown 文件新建/编辑做检查。每个合格框恰好一个入口；第二框插入后其他框及其选区不变；非目标字段无入口。
- 原生历史场景采用“已有文本 A → 插入命令 B → 再输入 C → 撤销/重做”。本次命令应整体撤销并重做，原有 A 和后续 C 的输入历史均保持可用。预览来回切换和 GitHub 重渲染后，文本仍保持一致。
- 文件编辑场景还要覆盖长文档、视口外内容、文中选区、文件名变化、路由前进/后退及旧请求过期。验证完整文档没有被视口 DOM 截断，文件预览读取到更新后的内容。
- 验证原生节点身份和顺序、Write / Preview、格式按钮、上传、提及、提交快捷键、暗色/高对比、窄窗口、键盘焦点和中文输入法。重复进入/退出编辑与页面导航后，没有重复入口、残留浮层或跨实例写入。
- 如果实施阶段可使用隔离测试仓库，在明确允许的测试目标上验证一次真实持久化；默认自动化不提交用户草稿。没有完成提交验证时必须在验收记录中标明，不能将预览成功描述为已验证持久化。
- 验收记录包含测试日期、Chrome/Edge 版本、GitHub 页面类型与测试结果。README 和 Issue 的实页写入、状态同步、预览与原生撤销全部通过，才可把首版标记完成。

## Out of Scope

- 替换 GitHub 编辑器、富文本/WYSIWYG、实时双栏预览、自定义 Markdown 渲染器、接管表单提交或自动保存。
- 表格、任务清单、脚注、自定义模板和模板同步；这些命令可以在后续版本按独立验收标准添加。
- PR、Discussion、Review、Wiki、GitHub Enterprise、github.dev、Codespaces 和移动端的兼容性声明。
- 修改 GitHub 仓库内容、自动提交 Issue、后台调用 GitHub API 或上传用户正文。
- 为某一 GitHub 页面变体绕过原生状态与撤销要求的隐藏降级方案。

## Further Notes

- [详细设计](design.md)保留菜单示意、编辑计划契约、具体边界和实施阶段说明；[官方来源研究](research.md)记录每项接入判断的证据和待验证处。本文是首版实施与验收的正式范围定义。
- 用户已确认以真实 GitHub 页面作为主要验收接缝，Markdown 文本转换采用少量有针对性的单元测试。
- Chrome/Edge 范围由用户明确选择。八个首版命令和后续命令排序来自现有设计；用户此前没有逐项确认菜单文案，实施时可在不改变命令语义与验收范围的前提下微调呈现。
- GitHub 开源 Markdown 工具栏允许自定义按钮，但不构成 GitHub.com 第三方扩展的稳定接入承诺。Issue Forms 的代码字段必须排除；GitHub 文件编辑使用 CodeMirror，但版本及实例访问方式需要真实页面验证。
- Spec 标为 `ready-for-agent` 表示开发任务与停止条件已经写清，**不表示** GitHub 运行时接入、撤销或 README 写入已经被证明。若 README 的最小探针无法通过，实施者应带着复现与证据回报阻塞，再调整方案或范围。
